## 0. 先に決める販売の停止条件

**本製品は現時点では販売不可**。暦の本番計算M06/N01／候補年の人間による検証N05、正式事業者、契約・返品・決済、本人限定納品、G2-C/S/L/Dの承認前に、商品ページを公開販売中と見せたり、購入ボタン、決済リンク、予約受付、メールでの仮受注を設けない。

- P00〜P07は開発用の設計画面IDであって公開URLではない。G2以前は非公開のサンプル／テスト環境だけで扱う。
- 無料診断の結果を見られる権利は購入しなくても維持する。登録した人だけが買える設計も採用しない。
- 事前に計算が不可能・対象外・根拠不足と分かった人からは**課金しない**。暦の候補年を本人の過去申告に合わせ事後変更しない。
- **支払済みで納品不能**は「完了」にしない。顧客への説明と契約条件に応じた再履行／解除／返金を人が判断できる。
- 配信停止や個人データ削除の要求は購入の有無に関係なく別ルートで受付。法定の取引記録と広告CRMを混ぜない。
- 本仕様は法律専門家による最終的な適法性承認ではない。

**事前の適用判定が成功しただけでは納品できる保証ではない**。本番取引前には、基礎暦の根拠・版、商品の対応範囲、制作可能な運用体制をG2-C/Sで確認する。対象外・不明・境界にある場合、申込みを承認しない。対応できない人を**別の安価な無料診断へ黙って差し替えて課金しない**。

取引時には最小限の連絡先と注文IDを使う。無料5問の匿名結果はLEAD-01の同意とも購入者IDとも自動結合しない。生年月日・本人の回答を解析イベントへ送らない。AIへの推敲入力は送信先・処理国・保持・委託関係の審査が終わるまで未承認。

## 5. P05：注文最終確認と決済設計（L/D）

### 注文直前の画面で必ず読める項目

1. 正式商品名・購入件数・提供内容・鑑定書の形式と含まれる範囲。
2. 消費者が支払う**税込総額・追加費用**。
3. 支払方法・支払時点、注文が確定する操作。
4. 鑑定書の提供方法・具体的納品時期。
5. 制作前／制作中／納品後のキャンセル・解除・返金条件。
6. 受付期間を実際に設定する場合、その期間。
7. 正式販売事業者・特商法表示・問い合わせへのアクセス。
8. 注文を戻って訂正できる操作と、購入確定であることが一目で分かるラベル。

**合意内容の版をorder_terms_snapshotとして取引記録に保存する案**。個人データを公開GitHubに保存しない。確認表示の正しさは実際に採用する決済導線の画面を用いて検査し、「決済サービス側に全部任せた」では合格にしない。

### 状態管理（同じ注文に3つの独立軸）

**注文・適用**：draft → eligibility_checking → eligible／ineligible／manual_review → checkout_ready → payment_pending → accepted／cancelled。acceptedから納品処理へ。適用不可ならcheckout_readyへ遷移不可。

**決済**：not_initiated → pending → paid／failed／expired／cancelled／manual_review。paid→refund_pending→partially_refunded／refunded／refund_failed。決済の「成功」は画面遷移・クライアント入力で決めず、署名／注文ID／通貨／金額／支払確定をサーバで照合。

**制作・納品**：not_started → queued → generating → qa_pending → approved → ready_for_delivery → delivered／delivery_failed → closed。生成・品質NG→generation_failed／qa_rejectedで停止。**deliveredは顧客が安全に取得できる状態と、納品条件に照らして定義**し、「メール送信APIが成功した」ことだけで納品完了としない。

取消や返金に伴う状態は注文と決済と納品を整合させ、処理の全順序・実際のAPIはMK09実装時にレビューする。状態のロールバックや納品済みへの虚偽の手動変更を禁止する。

### 支払い通知の防御

- サーバ側で決済セッション作成。税込額・通貨・商品IDは信頼するサーバ側で決定し、ブラウザからの料金変更を受け入れない。
- 同じ注文への決済作成は冪等化。注文ID・試行IDと支払いプロバイダIDを保護DBで対応付ける。
- Webhookの生ボディを使った署名検証、再送／異順到着／重複イベントの識別、金額・JPY・商品・注文状態の再検査を実施する。
- 非同期支払いは「支払い待ち」のまま納品せず、確定イベントだけで制作キューに入れる。遅延決済失敗時は未請求状態を明確化。
- 同一イベントが届いても**二重課金・二重制作・二重納品・二重返金にしない**。プロバイダの冪等化だけでなく自社DBで一意制約・トランザクション・ジョブ冪等性を持つ。
- 失敗・期限切れ・ユーザーが画面を閉じた場合は、**「支払失敗」か「支払済み」かを推測せずサーバと照合**する。
- 全決済の本番鍵・Webhook秘密鍵は秘密管理に格納。ログ、フロント、GitHub、デバッグ画面へ漏らさない。

## 6. P06：PDF生成・本人限定納品

### 鑑定書生成の品質ゲート

- 入力に紐づく暦方法版・rule_id・年候補・出典版が全件整合する。本人の振り返り回答から計算済み年を作り替えない。
- 未検証の年、空の根拠、年の捏造、具体的な人生事実の断定、個人識別情報の混入を検出したら**generation_failed／qa_rejected**として納品停止。判定はリリース候補版に残す。
- 個別PDFの生成元データとテンプレート版・レビュー版・ファイルのハッシュ値などの追跡可能性を確保する。ただしログに生年月日・相談・鑑定本文を出さない。
- PDFの日本語検索・文字選択・見出し・改行・アクセシビリティ・スマホ閲覧・破損検査を行う。**発行・納品テストは架空データ**で実施。
- 生成済みの非公開PDFは**認可された非公開領域**に保存。クラウドのpublic bucket・公開GitHub・検索エンジンに置かない。

### 本人限定ダウンロード

- 注文の所有権をサーバで照合してから、その注文の対象PDFへアクセス可能とする。**UUIDが推測困難であることだけで認証／認可の代わりにしない**。
- 第一候補：本人が確認したメールへの短命なアクセス用トークン＋注文単位の認可、または適切に認証された顧客ポータル。**メールが見られる＝絶対本人であるとは証明できない**ため、リスクと追加認証の必要性を審査する。
- 短命・一回限り／少数回制限のトークンを用い、原文ではなくダイジェストをサーバ保管。URLを広告・アクセス解析・リファラ・通常ログに残さない。期限・回数は運用を確定するまで**未決**。
- 別のテスト顧客の注文番号・PDF識別子へ変更しても**403／404等で取得できない**。取得ごとに所有権検査し、CDN・ブラウザ・メール転送・バックアップの漏えい経路を検査。
- PDFダウンロードの応答ヘッダ・キャッシュ・CSP、PDFファイル名・メタデータに不要な生年月日や姓名を含めない。公共PCでの保存についても案内を検討。
- 納品通知メールでは注文に必要な最小の情報だけ案内し、診断結果・個人の過去・PDF本文をメール本文に記載しない。
- 再取得はP07で本人確認・注文権限・納品状態を再評価し**新しい短命リンク**を発行。長期間の共有リンクを使わない。
- 法定取引記録・納品と鑑定本文の保管は別期限。正確な期間、削除、バックアップ・再生成規則は事業者・決済・PDFホスト決定後にMK05/MK07で確定。
- 顧客がPDFを受け取れること、文字化けがないこと、第三者が取れないことをE2Eで実際に証明するまではG2-Dを合格にしない。

## 7. P07：再取得・キャンセル・返金・問い合わせ

| ケース | 必要な判断／動作 | 関連するゲート |
| --- | --- | --- |
| 購入前に計算不能・出生境界保留 | 注文不可。料金を取らず理由を説明 | G2-C |
| 注文確認後、支払未成立 | 決済状態を確認し、結果確定まで制作・納品しない | G2-L |
| 支払済み、制作開始前の購入者キャンセル | 表示した契約条項と法令に照らし、解除と返金を審査 | G2-L |
| 制作中の変更希望・キャンセル | 制作段階・契約類型・利用者への説明に従って個別対応 | G2-L |
| 納品遅延・生成失敗 | 追加注文を自動作成せず、新しい期限の説明と再履行・解除・返金を判断 | G2-L/S |
| 内容に根拠のない年・誤算 | 納品停止または配布無効化、検算・訂正・再発行。必要に応じて契約解除・返金 | G2-C/S |
| PDF破損・ダウンロード不能 | 本人確認後の新リンクと代替方法。個人情報漏えい疑いは別扱い | G2-D |
| 他人の鑑定書を閲覧できる・誤配信 | 配布・新規受注を即停止、アクセス遮断、影響調査・法定報告／通知判定、是正・返金等 | ST05・G2-D |
| 重複課金・誤金額・返金失敗 | 取引台帳と決済会社を照合し、適切な取消・返金。未復旧なら販売停止 | ST04/ST06 |

| 個人データの訂正・削除 | 本人確認、処理停止・消去を検討。法定取引記録は独立して保持根拠を判断 | MK07・G2-D |

**契約上未決定のもの**：キャンセル期限、返金割合、納品期限、問い合わせ応答目標、再取得可能期間。任意の数字を法的基準や確定条件と偽らない。正式販売主体、スタッフ数、実際の制作工程から無理なく履行できる条件を設定して法務確認を通す。

**問い合わせの最小ワークフロー**：受付（非公開窓口）→本人確認→注文・納品・返金・個人情報の種別に振り分け→担当者対応→顧客通知→記録→必要に応じて修正・再試験。公開SNSの返信やGitHub issueで出生・相談を聞き取らない。未納品や漏えいは優先処理とし、停止・事故報告規則を参照。

## 8. データ契約の分離と管理

**orders（取引保護領域）**：order_id、product_id、terms_snapshot_version、amount_total_yen、currency、eligibility_status、payment_status、fulfillment_status、contact_ref、provider_payment_ref、created_at、updated_at。

**reading_jobs（機密の鑑定処理領域）**：job_id、order_id、calendar_method_version、evidence_refs、candidate_years_locked_at、reflection_status、render_version、qa_status、artifact_ref、created_at。生年月日・自由記述は必要に応じ別の暗号化領域に保持し、関係者以外はアクセス不可。

**payment_events（保護領域）**：provider_event_id（ユニーク）、order_id、verified_signature、event_type、provider_status、received_at、processed_at、outcome。生カード番号・決済秘密鍵は持たない。

**delivery_grants（保護領域）**：grant_id、order_id、artifact_ref、token_digest、expires_at、max_uses、used_count、revoked_at。原文の署名トークンをログに出さない。

**refund_requests（保護領域）**：request_id、order_id、reason_bucket、legal_review_status、provider_refund_ref、amount_yen、state、created_at、resolved_at。

**support_tickets（非公開領域）**：ticket_id、order_id?、case_type、customer_verified、state、owner_role、created_at、resolved_at、decision_ref。自由相談の丸ごと複写を避ける。

**order_audit（追記型）**：event_id、order_id、actor_role、action、old_status、new_status、timestamp、evidence_ref。機微データ・秘密鍵は記録せず、アクセス権と保存年限を別途検証。

- MK07のCRMと注文DBを**原則分離**。購入＝広告メール同意ではない。分析へ送るのはMK08の確定購入・返金などの**集計件数と金額**のみ。
- 注文の決済・商品提供に必要な通信は安全・法務レビューで対象を確定。外部AI・PDFホスト・決済会社・メール会社と委託／第三者提供・外国移転を契約単位で判断する。
- 最低権限の管理者、MFA、監査ログ・鍵管理・暗号化、環境分離、秘密鍵のローテーション、漏えいインシデント、バックアップ復旧時の削除反映を運用設計。
- 個人情報の保持と消去を、法定取引・精算、PDFの再取得、相談本文、広告同意の**別目的**ごとに設計。法定年限や実際の事業者設定は未確定。
