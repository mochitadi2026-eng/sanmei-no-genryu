# もちもち占術｜開発原則・品質ゲート v1.0

記録日：2026-11-02  
位置づけ：**今後の設計・実装・監査に適用する継続ルール**。この文書を作成したことは、実装・テスト・本番公開が済んだという意味ではない。  
適用範囲：`projects/mochimochi-jutsu/` の設計・検証。実際の算命学計算本体がある `tadi-sanmei-desk` には、そのリポジトリのルールと公開条件も併用する。

## 0. 最も大切な原則

> 正確に決められるところは、根拠と再現手順を残して決める。  
> 決められないところは、無理に決めず保留する。  
> 占いの物語は楽しめるものにするが、事実・計算・本人の回答を偽らない。

**何かを必ず当てることより、何を判定できて何を判定できないか説明できることを優先する。**

## 1. 事実と創作の分離

| 記号 | 対象 | 必須の確認事項 |
| --- | --- | --- |
| F | 古典・史料に記述された事柄 | 書誌、該当箇所、成立・刊行時期、本文確認範囲。存在の確認と実証効果は別 |
| R | 現代の命理・暦・算命学の計算・運用 | 対象の流派、入力条件、採用暦、境界、方式・データ・コードの版 |
| O | もちもち占術の新規アイデア、キャラ・質問・タイプ | 何を創作したか、旧案から変えた理由、利用者にどう説明するか |

F/R/Oは「由来・性質」の区分。親研究のA〜Fという**証拠の等級**とは別。古典に「当たる」と書かれていたとしても、実証的な的中能力は裏付けられない。

## 2. 三層分離を設計・コード・画面で守る

```text
出生・暦の条件 ─(M06の検算)─> もち質：伝統記号と解釈の境界
                                   ┐
5問の本人回答 ─(M07/M08の検証)─> もち具合：回答で選んだテーマ／フェーズ
                                   ┘ 由来を明示して並べる
                                    ↓
                             もち道：本人が選べる提案
```

- もち質：陰陽、五行、十干十二支、60干支、十大主星・十二大従星等の**象徴**。実際の暦・節入り・日界・蔵干・流派の計算検証（M06）が必要。
- もち具合：本人の**今の選択**に応じたMOCHI・KETSU・NUKI・NEBA・YURA・EN、12もちタイプ候補、現在の5フェーズ。出生情報で回答を補完しない。
- もち道：相談者が選べる小さな行動・問い。結果を保証せず、別の選択を拒否しない。
- 同じ12という数だけで十二支・十二大従星と12もちタイプを自動対応させない。既存の十大主星10キャラ＋大従星12式神は独立した物語役。
- 5問から6つの独立した能力・人格・医学的特徴を科学的に測定したとは書かない。スコア0〜100、偏差値、ランキングで偽の精密さを演出しない。

## 4. 変更管理

- 既存の**ファイル・関数・リポジトリを調べてから**新規作成する。作業を進めるためだけにリポジトリを増やさない。
- 仕様変更は **Before→After、変更理由、影響を受けるファイル・テスト、未解決事項** の5点を記録する。変えなかったことも明示する。
- IDは不変：`MOCHI`などの指標ID、`MT01`〜`MT12`、`FP01`〜`FP05`、`Q1`〜`Q5`、各選択肢IDを安易に再利用・付け替えしない。表示名だけを変えた場合もラベル版を管理する。
- 分類規則・回答文・選択肢の順序・絵・集計に影響する変更では、**question_version／tag_mapping_version／algorithm_version／必要なら画像版**を明確に更新する。
- 結果の再現には、判定版だけでなく実際の質問版・タグ版・タイプ対応版・画像版を照合する。古い回答IDを新しい対応表で無断に再解釈しない。
- 変更は設計、テスト、必要な読者向け説明、タスクボードの順で整合させる。一次資料を改訂するなら親研究の出典・主張・未解決課題の管理も更新する。

## 5. 判定エンジンの安全な入力と出力（M08）

### 入力・状態

- `Q1`〜`Q5`の各回答は、質問バンクに実在する**選択肢ID**であることが必須。
- 未回答：`incomplete`、結果は未確定。未知のID：`invalid`、正しい回答として処理しない。
- `x`は合法な「決めない」という回答。回答済みだが対応テーマやフェーズやモードは`null`。未回答と区別する。
- 既存仕様にないプロパティ・バージョンずれは黙って無視して成功扱いしない（入力契約を固定し、拒否または明示的な互換処理）。
- 乱数・実行日の時刻・ブラウザのタイムゾーン・閲覧回数により同じ回答の結果が変わらない。
- birthDate、出生地、名前、性別、血液型、十二支、五行等を5問の判定へ勝手に混ぜない。

### 現行の暫定分類条件（M08にて実装・試験）

1. Q1・Q2・Q4から、各選択肢が明示した一つのテーマまたは`null`を取得。
2. **Q4テーマが存在して、かつQ1またはQ2と一致した場合のみ**`primary_theme`の候補にする。Q1/Q2だけの一致では確定しない。
3. Q5が `open`／`settle` の場合のみ、テーマ×モードのM04表からタイプID候補を返す。どちらか欠ければ`mochi_type_id=null`。
4. Q3からフェーズID候補を独立取得。タイプが出なくても、フェーズは本人の直接回答として表示可能。
5. 回答が変更されたら新しい入力全体から再計算し、以前の出力を流用しない。
6. `candidate_themes`の扱い・`status`／`reason`列挙値はM08で明文化する。実装に都合よく性格得点や根拠のない例外処理を追加しない。

これは**遊びとしての結果分類の仕様候補**で、個人の性格・行動・運気を予測できる証明ではない。

### M08最低限の合格テスト

| テスト項目 | 期待 |
| --- | --- |
| スキーマ | 欠損・無効ID・版不一致・余分な値・型の間違いを期待する状態で返す |
| 明示保留 | 5つの`x`を正しく取り扱い、判定不能でもユーザーを否定しない |
| Q1/Q2依存 | 2問一致・Q4不一致をタイプ確定させない |
| 12タイプ | 6テーマ×2モードが各1個、全タイプに到達可能 |
| 5フェーズ | 各フェーズとフェーズ保留の出力が可能 |
| 全組み合わせ | `7×7×6×7×3=6,174`通りを列挙して入力・出力・例外を検証 |
| 分類数の参照値 | M07候補Bで全列挙時、タイプ候補936通り、保留5,238通り、タイプごと78通り（**構造的な予測値**） |
| 決定性 | 同じ版と回答列で深い同一性。入力を変更したら結果が更新される |
| 不変条件 | 入力や元JSONを破壊しない／外部通信なし／ローカル処理のみ |
| 説明と計算 | 未判定は未判定と表示。タグの票数を能力値や心理的信頼度へ変換しない |

**テストの意味**：これらはプログラムが設計どおり動くことの点検であり、6指標の心理学的妥当性、12タイプが本人に当てはまる割合、未来を予測できることを証明しない。

## 6. 生年月日・暦・算命学エンジンの検証（M06残件）

- 実際の計算コードは`tadi-sanmei-desk`の開発ブランチ／Draft PRにある。2026-11-02の監査時点で**mainには`lib/sanmei/`がない**。
- 既存Actionsの境界144入力と独立節入り36件の合格記録を認める。ただし今回新たに再実行した事実と混同しない。
- 2024〜2026の公式暦要項の節入りは分単位。監査ライブラリの秒単位計算と食い違うケースで、参考データの分表示を「秒までの真値」と扱わない。
- 暦・時刻は、計算エンジンの**対象年代・タイムゾーン・節入り±1分・日界23:00対0:00・1948〜1951日本夏時刻・出生地・歴史時計・蔵干／二十八元・流派の星配置**を別々のテストケースにする。
- 採用流派の一次資料、広範な日干支・十二大従星120ケース、1900〜2027独立照合が残る。未確定のものは`needs_review`、`unsupported`、または未提供とする。架空の出生時刻で穴埋めしない。
- **暦計算が一致しても、性格や未来の予測力が確認されたわけではない。**
- M06の本番判定を合格へ変更するには、参照日付・出典・期待値・実際値・使用したブランチ／コミット・実行ログを保存して判断する。

## 7. 安全、説明責任、プライバシー

- エンタメ的な問いかけと医療・心理検査を区別。自傷、疾病、妊娠、寿命、経済損失の予言や不安を煽る販売はしない。
- 開発や検証に使う例示出生情報・回答は**架空のもののみ**。実際の人物の相談履歴を公開GitHubに置かない。
- 5問の試作は、原則ブラウザ内で処理し、サーバーへ勝手に送信しない。外部AI API、外部の解析サービス、共有機能は初期仕様に含めない。
- 表示前に「娯楽的な自己理解の質問」「当てはまらなくても問題ない」「中断可能」「保存・削除の扱い」を説明する。保存や共有を増やす場合は**明示的・別個の同意**とM12の審査が必要。
- キャラ・画像制作で実在する神社や伝統を勝手に公式認定のように表現しない。六つの絵の要素の大きさ・色・視認性が回答誘導になる可能性を点検。
- 利用者の自由を守る。「運勢が悪いから必ず○○を買うべき」「休めない人は弱い」「MOCHIが低いから頑固」など断定・劣等化をしない。

## 8. 作業の単位と終了の定義

作業は**観測→判断→変更→検証→記録**で一件とする。

| 状態 | 言えること | 言えないこと |
| --- | --- | --- |
| 仕様作成済み | Markdown・JSONをコミットして参照可能 | 実行するエンジンが完成 |
| 構造チェック済み | ID・候補数・到達可能性を機械的に検証 | 利用者の分類妥当性が実証された |
| 単体テスト済み | 該当のコード・コミットに対してテストが成功 | 他ブランチや本番の動作が確認された |
| 一次監査済み | 対象のコード・既存のログ・参照資料を確認 | 全年代・全流派の照合完了 |
| CI成功 | GitHub Actionsで当該コミットのジョブ成功 | ブラウザー表示、デプロイ、本番公開が完了 |
| 本番反映済み | 実際の公開先・反映コード・挙動が別途確認された | 科学的な性格診断・占いの正確性が証明された |

変更のたびに以下を揃える：

- [ ] 今どのリポジトリ／ブランチ／コミットで作業したかを特定。
- [ ] 既存の仕様・未完・過去の決定を確認し、不要な二重開発を回避。
- [ ] 変更前／変更後、理由、影響範囲、旧仕様との互換性を記録。
- [ ] テストを**実際に実行**し、コマンド・入力・結果と未実施項目を分ける。
- [ ] 必要なドキュメント・データ・コード・テスト・タスクを同期。
- [ ] GitHubへ書いたものは再取得し、ファイルと版を確認。
- [ ] 公開・デプロイ・募集受付の変更は、その依頼と確認がある時だけ。
- [ ] 最終報告は「確定した事実」「仮案」「未検証」「次の一件」に分ける。
- [ ] **TASKS.mdの進捗と再開位置を更新**。ユーザーが次回、前回の説明を繰り返さなくても続けられる状態にする。

## 9. 今後の実務上の注意

1. **名前だけそろえても成果物は完成しない。** 12もちタイプ・5フェーズの名称と、実際に回答から決められることは別。
2. **エンジンのテストとUIのテストは別。** スマホで操作できるか、途中離脱できるか、図と文が一致するか、画像に誘導がないかはM11/M12で確認する。
3. **検証で見つけた不一致を隠さない。** 採用方式の違いがあるなら流派・版・入力・期待値を記録し、改ざんした「正解」に合わせない。
4. **開発の進捗を、承認や公開と混同しない。** 現在の中心作業はM08の独立した判定器の実装。M06の本番合格とM12の公開審査は別の作業。
5. **迷ったら、まず現在の設計・コード・テストを読む。** 新規ファイル・新規リポジトリ・新規理論を増やして解決したことにしない。
