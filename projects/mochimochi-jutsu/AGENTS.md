## 作業を始める順番

1. [TASKS.md](TASKS.md)の「次に実施する一件」から開始し、完了済みの作業を無断でやり直さない。
2. [README.md](README.md)と[基本理論書](04-basic-theory-v0.1.md)で現在の設計と未決事項を把握する。
3. 変更対象の直接の元データ・仕様を読む。特にM08では[M07の質問JSON](m07-question-bank-v0.1.json)、[M04のタイプJSON](m04-types-phases-v0.1.json)、[M07の仕様書](06-five-question-design-v0.1.md)を先に読む。
4. 実行前に対象リポジトリ、現在のブランチ・対象パス・既存コードの有無を確認する。現在の作業は研究リポジトリの設計・検証であり、`tadi-sanmei-desk` の `main` や本番サービスではない。

## 絶対に守ること

- **事実・計算上の仕様・検証結果・推測・創作を混同しない**。原典F、現代実務R、独自創作Oを分ける。原典の出典等級A〜Fとは別の分類。
- **入力が足りないなら判定しない**。不明を都合のよい値で補完しない。未知の出生時刻を12:00とみなさない。診断の無回答と「決めない（x）」を混同しない。
- **人格や将来を断定しない**。心理検査・医療診断・霊的能力・科学的な性格測定として提示しない。低得点や未判定を人格的な欠点と解釈しない。
- **決まった仕様を黙って変えない**。ID・版・分類条件・画像・質問を変更するなら、理由と影響範囲、旧仕様からの差分を記録し、該当仕様・テスト・タスクを同期する。
- **正解の捏造をしない**。テストが成功したことを正確性や妥当性の証明と扱わない。GitHub Actionsの過去の成功を今回実行したと偽らない。やっていないテストは未実施と報告する。
- **個人情報を公開リポジトリに保存しない**。実際の出生情報・相談記録・回答・メール・トークンはコミットしない。例示データは必ず架空と表示する。
- **許可のない公開・サービス変更はしない**。`tadi-sanmei-desk` の `main`、Workers、GAS、既存募集フォーム、実利用者への自動送信、課金・販売・公開状態は独断で変更しない。
- **根拠のない優劣・相性・運気上昇を生まない**。五行・星・12タイプ・5フェーズ・6指標の役割を混ぜない。

## M08の直近ルール（更新版）

- 質問バンクの `question_version` と `tag_mapping_version`、M04のタイプ・フェーズID、判定器自身の版を固定する。
- 入力は回答文でなく `Q1`〜`Q5` の**選択肢ID**。存在しないIDはエラー、欠けた回答は `incomplete`、`x` は有効な意思表示で値は `null`。

- **全6,174組**、12タイプへの到達、5フェーズへの到達、未判定、バージョン不一致、決定性、改ざん入力、境界条件のテストを実行して初めて「M08の実装とテストを実施」と報告できる。
- 計算の構造検証と利用者に対する妥当性検証を区別する。無理に全員を12タイプに分類する条件へ変更しない。

## 変更の完了条件

1. 変更した実ファイルとGitHubのコミット・URLを確認する。
2. 関連する仕様書、JSON、テスト、[TASKS.md](TASKS.md)、必要なら[README.md](README.md)を同期する。
3. 完了報告は「実施したこと／確認できた証拠／未実施・未解決／次の一件」を分ける。
4. 全工程が実行・検証済みでない場合、「設計のみ完了」「一次監査済み」「実装未検証」「本番未反映」など範囲を明示する。
5. **作業を将来の提案だけで終わらせない**。できる範囲を現在の会話で実行し、GitHubへ実際に記録する。ただし出力の公開・デプロイ・記事化が今回の依頼範囲外なら独断で実行しない。
